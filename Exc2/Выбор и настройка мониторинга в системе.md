#### **Мотивация**

В качестве аргументов для внедрения мониторинга приведу как бизнес так и технические предпосылки:

1. Повышение прозрачности и контроля над системой
Текущая ситуация:

        Компания сталкивается с проблемами производительности (медленная загрузка MES, долгий расчёт стоимости изделий) и потерей заказов.

        Нет чёткого понимания, где именно возникают узкие места в системе.

    **Решение:**

        Мониторинг позволит в реальном времени отслеживать состояние всех компонентов системы (CRM, MES, API, очереди RabbitMQ).

        Это даст возможность оперативно выявлять проблемы и принимать меры до того, как они повлияют на клиентов.

2. Ускорение реакции на инциденты
    Текущая ситуация:

        Жалобы клиентов на просроченные заказы и потерю заказов поступают постфактум, когда проблема уже повлияла на бизнес.

        Операторы не могут оперативно получать информацию о новых заказах из-за медленной загрузки MES.

    **Решение:**

        Мониторинг позволит обнаруживать аномалии (например, сбои в обработке заказов или медленные ответы API) в режиме реального времени.

        Это сократит время реакции на инциденты и минимизирует их влияние на клиентов.

3. Оптимизация производительности системы
Текущая ситуация:

        Загрузка первой страницы MES занимает много времени, несмотря на внедрение фильтров и пагинации.

        Расчёт стоимости изделий может занимать до 30 минут для сложных моделей.

    **Решение:**

        Мониторинг поможет выявить узкие места в производительности (например, медленные запросы к базе данных, перегрузка очередей RabbitMQ).

        Это позволит оптимизировать систему и сократить время обработки заказов.

4. Предотвращение потери заказов
    Текущая ситуация:

        После открытия API для сторонних продавцов количество заказов резко увеличилось, но многие заказы теряются или не доходят до клиентов.

        Нет механизмов для отслеживания статуса заказов в реальном времени.

    **Решение:**

        Мониторинг позволит отслеживать поток заказов через CRM, MES и API, выявляя случаи потери или задержки.

        Это поможет предотвратить потерю заказов и улучшить клиентский опыт.

5. Снижение операционных рисков
    Текущая ситуация:

        Потеря заказов и недовольство клиентов создают риски для бизнеса.

        Нет механизмов для предотвращения сбоев и минимизации их последствий.

    **Решение:**

        Мониторинг позволит выявлять потенциальные риски (например, перегрузка системы, сбои в интеграциях) до того, как они повлияют на бизнес.

        Это снизит операционные риски и повысит устойчивость системы

6. Поддержка бизнес-целей
    Текущая ситуация:

        Проблемы с заказами и клиентским опытом негативно влияют на репутацию компании и её доходы.

        Потеря крупных контрактов из-за проблем с API.

    **Решение:**

        Мониторинг поможет обеспечить стабильную работу системы, что напрямую влияет на удовлетворённость клиентов и рост бизнеса.

        Это поддержит стратегические цели компании по расширению рынков сбыта и увеличению доходов.

#### **Выбор подхода к мониторингу**

#### MES
Для этой системы предлагается использовать подход USE (Utilization, Saturation, Errors)

Почему USE: MES — это ресурсоёмкий компонент, который зависит от CPU, памяти и диска.

    USE фокусируется на инфраструктурных метриках (использование ресурсов, насыщение, ошибки), что поможет выявить узкие места в производительности.

    Например, можно отслеживать:

        Utilization: Загрузка CPU и памяти.

        Saturation: Очереди задач в MES.

        Errors: Количество сбоев при расчёте стоимости.

#### RabbitMQ
Также как и для MES очередей использовать подход: USE 

Почему USE: RabbitMQ — это инфраструктурный компонент, который зависит от ресурсов (CPU, память, диск).

    USE поможет выявить проблемы с производительностью очередей:

    Utilization: Загрузка ресурсов сервера RabbitMQ.

    Saturation: Длина очередей сообщений.

    Errors: Количество потерянных или необработанных сообщений.

#### CRM
Для этой системы предлагается использовать подход RED (Rate, Errors, Duration)

Почему RED:
CRM — это компонент, который обрабатывает большое количество запросов от клиентов.

    RED фокусируется на скорости обработки запросов, количестве ошибок и времени выполнения, что критически важно для CRM.

    Например, можно отслеживать:

    Rate: Количество новых заказов в единицу времени.

    Errors: Количество заказов, которые не были обработаны.

    Duration: Время обработки заказа.

#### API для сторонних продавцов
Четыре золотых сигнала (Latency, Traffic, Errors, Saturation)

Почему Четыре золотых сигнала: API — это компонент, который напрямую влияет на клиентский опыт и должен быть максимально отказоустойчивым.

    Четыре золотых сигнала охватывают все ключевые аспекты производительности API:

    Latency: Время ответа API.

    Traffic: Количество запросов к API.

    Errors: Количество ошибок в ответах API.

    Saturation: Нагрузка на серверы, обрабатывающие запросы API.

#### Метрики для отслеживания

1. RabbitMQ
    - Number of dead-letter-exchange letters in RabbitMQ
        Для отслеживания количества сообщений, которые не удалось обработать и которые попали в Dead Letter Exchange (DLX). Это поможет выявить проблемы с обработкой сообщений.
    - Number of messages in flight in RabbitMQ
        для отслеживания количества сообщений, которые находятся в процессе обработки. Это поможет выявить перегрузку очередей.
Можно добавтить ярлыки для агрегации и группировок для ребита например queue_name и error_type

2. API (Internet Shop, CRM, MES)
    - Number of requests (RPS) for internet shop API          
        отслеживать нагрузку на API интернет-магазина. Поможет мониторить текущую нагрузку и спланировать масштабирование.

    - Number of requests (RPS) for CRM API  
        отслеживание нагрузки на API CRM. Нам поможет оценки производительности системы управления заказами.
    
    - Number of requests (RPS) for MES API
        чтобы отслеживание нагрузки на API MES а также отслежитьва быстро ли система справляется с расчётом стоимости изделий.
    
    - Response time (latency) for shop API
        важно для оценки пользовательского опыта.
        
    - Response time (latency) for CRM API
        поможет выявить задержки в обработке заказов

    - Response time (latency) for MES API
        отслеживание времени ответа API MES оценка производительности расчёта стоимости изделий.
    - Number of HTTP 200 for shop API
        для понимания количества успешных запросов к API интернет-магазина. Это поможет оценить стабильность системы.
    - Number of HTTP 200 for CRM API
        количество успешных запросов к API CRM для оценки стабильности системы управления заказами.
    - Number of HTTP 200 for MES API  
        количества успешных запросов к API MES для оценки стабильность системы расчёта стоимости.
    - Number of HTTP 500 for shop API
         количество ошибок на стороне сервера (500) в API интернет-магазина.
    - Number of HTTP 500 for CRM API
         количество ошибок на стороне сервера (500) в API CRM для выявления сбоев в обработке заказов.
    - Number of HTTP 500 for MES API
        количество ошибок на стороне сервера (500) в API MES для выявления сбоев в расчёте стоимости.
    - Number of simultaneous sessions for shop API
        количество одновременных сессий в API интернет-магазина для нагрузки на систему.
    - Number of simultaneous sessions for CRM API
        количество одновременных сессий в API CRM важно для оценки нагрузки на систему управления заказами
    - Number of simultaneous sessions for MES API
        количество одновременных сессий в API MES для нагрузки

Для данных показателей можно использовать метки endpoint, http_method чтобы понять графики в разрезе конкретной системы или методов при обращениях к ним.

3. Ресурсы (CPU, Memory)
    - CPU % for shop API
        загрузка CPU для API интернет-магазина для выявления узких мест в производительности.
    - CPU % for CRM API
        CPU для API CRM
    - CPU % for MES API
        CPU для API MES
    - Memory Utilisation for shop API
        отслеживание использования памяти для API интернет-магазина для предотвращения утечек памяти.
    - Memory Utilisation for CRM API
        отслеживание использования памяти для API CRM для оценки стабильности системы управления заказами.
    - Memory Utilisation for MES API
        использования памяти для API MES. Это помогает предотвратить утечки памяти

Здесь можно использовть ярлык например instance, service - для группировок и лакализации конкретного компонента

4. Базы данных

    - Memory Utilisation for shop db instance
        использование памяти для базы данных интернет-магазина. поможет предотвратить утечки памяти.
    - Memory Utilisation for MES db instance
        тоже самое для MES и стабильности расчета стоимости
    - Number of connections for shop db instance
         количество подключений к базе данных интернет-магазина

    - Number of connections for MES db instance
        количество подключений к базе данных MES важно для оценки нагрузки на систему.

Здесь также можно использовть ярлык instance - для группировок и лакализации конкретного компонента.

Здесь также можно использовть ярлык instance - для группировок и лакализации конкретного компонента.

        для API MES
    - Kb provided (sent) for shop API

    - Kb provided (sent) for CRM API
        для CRM API

        дял MES

#### План действий

1. Настройка инструментов мониторинга Создать инфраструктуру для сбора, хранения и визуализации метрик.
    - В качестве TSDB использовать Prometheus. Prometheus подходит для сбора метрик в реальном времени.
    - Настроить сбор метрик:
    Установить и настроить Prometheus для сбора метрик с API, RabbitMQ, баз данных и других компонентов.

    - Настроить визуализацию:
        Установить Grafana для создания дашбордов и визуализации метрик.
        
    - Настроить подключение Grafana к Prometheus

2. Интеграция метрик из компонентов системы - yастроить сбор метрик для каждого компонента системы для API (Internet Shop, CRM, MES):

    Настроить экспорт метрик (RPS, latency, HTTP-статусы) с использованием библиотек для мониторинга Prometheus client для Java бэкенда.
    Добавить ярлыки которые мы описали выше: endpoint, http_method

    RabbitMQ: 

        настроить сбор метрик через RabbitMQ Exporter для Prometheus.
        Добавить ярлыки описанные выше: queue_name, error_type.

    Базы данных: 
    
        настроить сбор метрик (количество подключений, использование памяти) через экспортеры для PostgreSQL/MySQL.
        Добавить ярлыки: instance.

    Ресурсы (CPU, Memory):

        настроить сбор метрик через Node Exporter для Prometheus.
        Добавить ярлыки: instance, service.

3. Создать дашборды в Grafana чтобы визуализировать ключевые метрики для удобства анализа.

    Создать дашборды для каждого компонента: API: RPS, latency, HTTP-статусы.

    RabbitMQ: количество сообщений в очередях, Dead Letter Exchange.

    Базы данных: количество подключений, использование памяти.

    Ресурсы: загрузка CPU, использование памяти.

    Добавить фильтры и группировки: используюя ярлыки для фильтрации данных (например, по endpoint, queue_name, instance).

4. Настроить алерты:
   
    - Создать алерты для критических метрик (например, высокий уровень ошибок, перегрузка очередей).
    Настроить каналы оповещений:

    - Подключить Slack, Email или другие каналы для отправки уведомлений.

    - Оповещение, если количество HTTP 500 превышает порог.

    - Оповещение, если загрузка CPU превышает 80%.

    - Оповещение, если количество сообщений в Dead Letter Exchange растёт.

Настроить эскалацию:
    определить, кто и как будет реагировать на алерты (например, разработчики, DevOps, поддержка).
